# MemQ MCP — development and release notes

The current local MCP prototype is a stateless Streamable HTTP Supabase Edge Function. It exposes `list_lessons`, `list_cards`, `create_lesson` (optional cards, atomic), `update_lesson`, `delete_lesson`, `add_cards`, `update_card`, `delete_card`, `create_lesson_with_practice`, `add_cards_with_practice`, `add_practice_questions`, `list_practice_questions`, `replace_practice_question`, and `delete_practice_question`. Each call uses the signed-in user's Supabase token and RLS-scoped client. The tools never accept a user ID from the model. Deleting a lesson also deletes its cards; both delete tools are marked destructive and require explicit confirmation. Language cards use the same `language_data` fields as the app.

**The direct-Supabase-OAuth prototype is blocked outside local development.** The handler returns 503 unless `MEMQ_UNSAFE_LOCAL_OAUTH_PREVIEW=true` and `SUPABASE_URL` is a recognized local HTTP host. For a disposable local project, put that flag in a temporary env file and pass it to `supabase functions serve --env-file ...`. This guard prevents an accidental deployment of the known-unsafe prototype; it is not the final authorization design.

## Before enabling for real users

1. Apply the lesson-cover migration and the `20261113100000_add_mcp_create_lesson.sql`, `20261113120000_add_mcp_update_card.sql`, `20261113130000_add_mcp_practice_questions.sql`, `20261113140000_add_mcp_cards_with_practice.sql`, and `20261113150000_track_practice_revision.sql` migrations to a staging database. Verify all existing lessons/terms policies, including insert `WITH CHECK`, with two real users. Do not run the destructive `reset_all_tables.sql` migration.
2. Replace the direct OAuth token exposure with an isolated authorization server and adapt the consent page. The existing `/oauth/consent/` page and Supabase OAuth configuration are integration prototypes, not the final release flow. Configure and test each sign-in provider and allowed redirect before use.
3. **Security gate:** Supabase OAuth user tokens can be presented directly to the project's Data API and other user-authenticated APIs, not just this MCP server. The token can confer access beyond the lesson and card management tools under the current RLS policies. Do not describe this as least-privilege access or make it public until token audiences/client-specific policies and all relevant tables/functions have been audited and constrained. Review client registration, consent, redirect URIs, revocation, prompt-injection handling, request limits, and logging.
4. Deploy only the replacement after verifying discovery, token audience and issuer, user consent, credential isolation, and every security gate. The prototype's Supabase middleware and gateway configuration are not a production authorization architecture.
5. Test unauthenticated discovery/401, token rejection, user isolation, consent approval/denial/revocation, refresh, empty/maximum/invalid batches, duplicate retries, and atomic rollback. Then test the real HTTP transport from each target client.
6. Check current per-client account, region, workspace and write-action restrictions before promising access. Clients may prompt separately for write confirmation. The endpoint requires public HTTPS.

The `preview/memq-website/oauth/consent/` page is a local integration draft. Hosting, deployment, Auth settings, and a production URL are not configured by this repository change. The listed public Supabase key is not a service key.

## Local checks

`deno test --node-modules-dir=none supabase/functions/mcp/tools_test.ts` exercises the MCP tool transport and mocked database calls. `./scripts/test-mcp-db.sh` starts an isolated, disposable Supabase Postgres container and checks creation, validation, database-error rollback, anonymous access, and cross-user RLS. It also holds a card edit open while attempting both an insert and an update of a question based on the previous card revision, verifying that both stale writes are rejected after the edit commits. The database fixture models expected RLS and is **not** evidence of the live project's policies. Both tests must pass before staging, and staging must still be tested with actual Supabase Auth and client integrations.

An end-to-end check has also run against a separate local Supabase project with OAuth 2.1 enabled: dynamic registration, PKCE, consent, lesson and card CRUD, isolation between two users, pagination, consent denial, refresh, and rejection of tokens after revocation all passed. The website consent page was exercised with a disposable local account. `scripts/test-mcp-oauth.py` can repeat the API portion when `MEMQ_MCP_TEST_WORKDIR` points to the explicitly named `memq-oauth-local` test project on port 55421. This does not validate hosted-provider configuration, social login, or production policies. The app's Connected apps screen is hidden unless `EXPO_PUBLIC_MCP_ENABLED=true`; enable it only when the OAuth rollout is ready.

## Read-only production policy inventory

`supabase/audits/mcp_security_readonly.sql` inventories RLS, table and sequence grants, views, callable functions (including SECURITY DEFINER), schema access and role inheritance without reading application rows or changing the database. `supabase/audits/mcp_security_inventory_json.sql` returns the same categories as a single JSON row for SQL editors that display only one result. Run them only as a read-only review in the correct project's SQL editor. Their results must be assessed against OAuth `client_id` and all exposed schemas, storage policies, and Edge Functions; neither query restricts access. The complete inventory has not been run against production; a targeted review is recorded below.

On 2026-11-14, a targeted read-only review of the live MemQ project's metadata found that `lessons`, `terms`, `questions`, `profiles`, and progress tables have RLS enabled and the inspected ownership policies use `auth.uid()`. Progress and other personal data remain available under the user's identity, so an upstream Supabase OAuth token is not lesson/card-only. The `pdfs` bucket is marked public and has a `Public can read PDFs` SELECT policy covering that bucket. PDF contents and object lists were not accessed. The app previously generated public PDF URLs and passed them to `process-file`, so changing the bucket to private requires updating and validating the upload/processing flow first. The inspected live schema has `lessons.learning_mode`, but lacks `lessons.cover_style`, `terms.content_revision`, and `questions.source_revision`; the inspected public callable-function list did not contain the MCP RPCs. No live settings or migrations were changed by this review. This targeted review does not cover every role, policy, privileged function, edge function or external integration.

Local changes now prepare a private-PDF rollout: both app upload paths request 15-minute signed URLs, and `process-file` accepts legacy public or signed URLs only for the authenticated user's path on the configured project, then issues its own short-lived URL under that user's Storage permissions. It no longer prints upstream error bodies or model output, which could expose URLs or PDF contents. `supabase/audits/pdf_private_candidate.sql` is a review-only candidate, deliberately outside migrations. In a disposable database fixture it removes the known public SELECT policy and verifies anonymous denial and per-owner access. Before changing live storage, test the Edge Function and actual MinerU retrieval with synthetic PDFs in staging, verify all existing bucket policies and consumers, deploy and verify the backward-compatible function first, assess older app versions and cached public copies, then obtain approval for the live bucket/policy change. A signed URL is a bearer link until it expires, and the PDF is still sent to MinerU for parsing. No production change has been applied.

An isolated Node test runs a transpiled copy of the Edge Function with mocked Auth, Storage, MinerU and model calls: it checks legacy URL conversion, cross-user rejection before processor access, and that an upstream error echoing a signed token is not logged or returned. This is not a Deno deployment test and does not prove real signed-URL retrieval or MinerU behavior.

`scripts/test-pdf-storage-local.py` separately exercises real local Supabase Auth and Storage in the explicitly named disposable audit project. ## Production permission findings (2026-11-13, read-only dashboard audit)

- OAuth Server is disabled. Existing `lessons` and `terms` policies allow all operations for `authenticated` users on their own content; OAuth tokens using that role would therefore be broader than the three MCP tools.
- The production `public.update_subscription_status(uuid, boolean, timestamptz, text)` function is `SECURITY DEFINER`, accepts an arbitrary user ID, has no authorization check, and is executable by `anon` and `authenticated`. This can allow untrusted callers to change subscription fields. Do not test this against real users.
- `authenticated` has table-level INSERT and UPDATE rights on all six `profiles` columns, and the existing own-profile policy permits a user to update their own row. Row-level security alone does not prevent changes to subscription columns.

`supabase/migrations/20261113110000_protect_subscription_permissions.sql` was applied to production through the SQL Editor on 2026-11-13 after explicit approval. It removes untrusted execution of the subscription function and direct profile write privileges, preserves authenticated `INSERT(id)` for default-valued profile recovery, and preserves `service_role` execution. The isolated database test verifies those cases. The checked-in app reads these subscription fields but has no direct profile update or direct call to the function. External clients or webhooks are not inventoried; confirm their use of `service_role` before deployment. The mitigation does not solve the separate broad MCP OAuth token scope; that remains a release gate.


### Production fix verification (2026-11-13)

After the approved SQL transaction, a read-only privilege check returned: `anon` and `authenticated` cannot execute `update_subscription_status`; `service_role` can execute it; authenticated users cannot update `is_pro` or insert `subscription_plan`; and authenticated users retain profile SELECT and INSERT on `id`. The signup trigger was confirmed enabled and owned by `postgres` with `SECURITY DEFINER` before the change. No production user rows were changed by the migration. The SQL was applied manually in the dashboard and may not be recorded in Supabase migration history; the migration is idempotent and should be reconciled with that history before a future migration push. External integrations were not inventoried and should be monitored for clients that previously relied on ordinary-user profile writes.

## Service-role Edge Function gate (draft; not deployed)

An OAuth access token is a valid user token and can otherwise reach existing functions that use a service-role client. In particular, the checked-in `delete-account` function verifies the user, then deletes the account with elevated privileges; row-level policies cannot restrict that path. The local changes to `delete-account`, `update-term-progress`, `chat-history`, `chat-thread-messages`, `chat-delete-thread`, and `chat-assistant` reject OAuth Server sessions after `getUser()` verifies the bearer token. The shared parser is deny-only and never substitutes for token verification. These changes are not deployed.

The local `generate-questions` and `generate-vocab-questions` functions now verify the direct user session and ownership of the lesson and every supplied card, and write generated questions using the user's RLS-scoped client instead of service-role credentials. The shared check has unit tests covering authenticated ownership, foreign lessons and cards, invalid IDs, OAuth sessions, and database errors; these mocks do not establish real database policy behavior. These changes are not deployed or validated against production RLS; test both direct app flows in staging first. The two question generators now use OpenAI SDK 6.49.0; their Deno type checks pass and a mocked request test verifies the existing request parameters. Live model calls still require staging validation.

The local `generate-terms`, `generate-vocab-terms`, `process-file`, and `chat-extractor` functions also verify a direct app user with Auth before performing paid API or file-processing work; OAuth client tokens are denied. Their shared validation fails closed if Auth fails, and is unit tested. These guards are not deployed. Test email and configured social-provider app sessions against each endpoint in staging before rollout. The generation and extractor functions have existing OpenAI SDK type errors; `process-file` additionally depends on a remote Deno module unavailable in the offline test environment.

`supabase/audits/mcp_oauth_rls_candidate.sql` is a staging-only candidate for restricting OAuth access to known personal tables using restrictive policies while leaving existing lesson and card ownership policies intact. The isolated database test models the six restricted personal tables and verifies direct-session reads, OAuth denial, lesson/card/question access, and lesson deletion cascading to cards, questions, and progress. This is not a complete boundary: it does not cover undiscovered tables, views, storage, privileged functions, Auth APIs, or deployed code. Inventory those separately and test all actual policies and app flows before any deployment. The fixture provides a mock `auth.jwt()` because the isolated database image lacks the full Auth schema; it is not evidence of production behavior.

In a separate disposable Supabase project, the candidate was also tested with a real OAuth token and the real Auth `auth.jwt()` function. The test confirmed direct-session insert/read and OAuth read/insert denial on a representative progress table, while lesson/card CRUD and token revocation continued to work. Set `MEMQ_MCP_TEST_RLS=1` when running the local OAuth test against a test project provisioned with `supabase/tests/mcp_oauth_live_fixture.sql` and the candidate policy. This does not validate the live project's schema or other API surfaces.

### Auth API boundary finding

With `MEMQ_MCP_AUDIT_AUTH=1`, a disposable local OAuth user successfully called `PUT /auth/v1/user` using the OAuth access token and changed that user's Auth metadata; a subsequent direct-session read confirmed persistence. The test changed no real account. This endpoint is outside Postgres RLS, so the candidate restrictive policies do not prevent it. The current Supabase-issued OAuth token therefore does not implement the user's requested lesson/card-only authorization boundary even if all table policies are restricted. Do not enable or publish this OAuth design as a lesson/card-only connection. Evaluate a separately issued, MCP-audience access token validated by the MCP service, with any upstream account credentials held server-side and never returned to the client; independently audit broker credential storage, rotation, revocation, and all service-role operations. Confirm the architecture and provider capabilities in staging before implementation or production use.

The selected prototype uses a separate OAuth authorization server issuing MCP-audience tokens, with Supabase sign-in and consent on the existing website and the upstream user credential kept in encrypted server-side grant state. The MCP service validates its own tokens and invokes the existing user-scoped lesson/card code with the upstream session. Consent/PKCE handoff, refresh-token rotation and per-client revocation are implemented and exercised locally as described below; production hosting, KV configuration, distributed behavior and operations still require staging validation. See https://developers.cloudflare.com/agents/model-context-protocol/protocol/authorization/ and https://github.com/cloudflare/workers-oauth-provider/blob/main/docs/advanced-configuration.md.

The broker prototype lives in `mcp-broker/`. It connects Cloudflare's OAuth provider, client-specific consent, a Supabase authorization-code/PKCE handoff, encrypted provider grant props, and the user-scoped MCP tools. Its upstream module handles refresh-token rotation and verifies the Supabase user ID; revoked and transient failures are distinguished without logging credentials. The checked-in Worker defaults to disabled and uses a placeholder local KV binding. When explicitly enabled, it requires the request origin to match the configured broker origin, HTTPS for non-local origins and upstreams, and non-placeholder OAuth settings. `npm test` checks input escaping, upstream exchange behavior, and synchronization with the canonical MCP tools. A local Wrangler runtime returned protected-resource metadata and correctly challenged an unauthenticated MCP request.

The broker consent page uses the current site's Geist/Oswald typography, lime gradient, purple actions, and rounded card. A headless Chrome inspection of a static rendered example at 320, 390, and 1280 CSS pixels found no horizontal overflow; a long unbroken client name also stayed within the narrow viewport. Reduced-motion styling and keyboard focus indicators are provided. This inspection did not exercise the live browser authorization redirect or production font availability.

The website's separate upstream consent prototype defaults to `CONSENT_ENABLED = false`; it does not initialize Supabase sign-in while disabled. A disposable browser fixture must explicitly enable it and use its own test project configuration. This client-side switch is an accidental-publication safeguard, not a security boundary: the upstream OAuth server and broker must remain disabled or independently protected until the full authorization design is verified.

An automated local HTTP flow (`mcp-broker/scripts/test-local-broker.py`) has now exercised client registration, consent, Supabase PKCE sign-in, broker token issuance, lesson/card CRUD, refresh, cross-account isolation, denial and replay of consent, revocation of one client without disrupting another client for the same user, and a two-request concurrent refresh in one local runtime against a disposable Supabase project and a local Wrangler Worker. The test confirms the broker token is rejected by Supabase Auth. It simulates the browser's secure-cookie handling and Supabase approval with HTTP calls; it is not a full browser or hosted-provider test. Worker fetch uses `redirect: 'manual'`, with redirects rejected by the normal non-success handling, because `redirect: 'error'` is unsupported by the Worker runtime.

The card update RPC merges supplied language-detail fields atomically instead of replacing the whole object, while an explicit `null` clears it. Both the isolated database test and local broker flow verify preservation of existing details; cross-user updates are denied. The new migration is local only and is required before deploying the updated tool.

`20261113150000_track_practice_revision.sql` adds card/question revision tracking. A meaningful card edit changes its revision, making earlier questions stale; the MCP lists them with `is_stale`, and both practice screens exclude them when the migration is present. An explicit question replacement records the current revision. If the database lacks these columns, the app retains legacy loading behavior, so this migration must be deployed before relying on stale-question filtering. Existing questions are backfilled to the card's revision at migration time: their historical correctness cannot be established automatically. Review migration locking, backfill duration, existing privileges and policies in staging before production. Local tests cover no-op edits, stale detection, refresh, and PostgREST's missing-column fallback code.

The local broker now has connection-list and grant-revocation endpoints. They verify a direct Supabase user session, reject OAuth access tokens, and operate only on grants keyed to that user. The local HTTP test exercises listing, rejecting an MCP token, preventing another user from revoking the grant, and revoking one of two clients. The app's feature-gated Connected apps page now targets this broker via `EXPO_PUBLIC_MCP_BROKER_URL`; it must remain disabled until a deployed broker is configured and tested. Browser access can be enabled for one exact origin with `APP_WEB_ORIGIN` (HTTPS except localhost); it is disabled when unset. The origin matching is unit-tested; local Worker preflight requests returned 204 with the expected headers for the configured origin and 403 without CORS headers for another origin. A real browser's authenticated flow and the native screen's end-to-end behavior remain unverified.

This is not release-ready: multi-region concurrent refresh and revocation consistency, actual app consent design/hosting, and hosted-provider behavior have not yet been tested with the broker. The Supabase OAuth client and callback are unconfigured, the checked-in resource origin is local and no Worker has been deployed. Token expiry handling and provider KV consistency must be examined under concurrent refresh before production. CIMD is disabled in the local config to permit local development; a production configuration must use `global_fetch_strictly_public` and validate metadata URL fetching before enabling it.

`mcp-broker/scripts/test-browser-broker.py` was run with a real headless Chrome mobile viewport, a disposable local Supabase account, a temporary copy of the website's actual consent UI configured for the local project, and a local Worker. It clicked broker consent, signed in through the MemQ page, approved upstream access, returned to the client callback, exchanged the code, and called the MCP endpoint. It does not validate production hosting, social-provider sign-in, or the native app's Connected apps screen. The test needs Python's `websocket-client` and locally running test services.

This is not a complete production boundary: inventory every deployed Edge Function and API that uses elevated credentials, including code not checked into this repository. Confirm deployed function versions and behavior in staging; do not infer production coverage from local source. The existing `chat-assistant` function's independent OpenAI SDK type incompatibility (`reasoning_effort: 'none'` versus its pinned SDK) prevents a clean Deno type check of that function; the other five previously changed functions type-check successfully.

The MCP client’s own model writes practice questions and submits them with `add_practice_questions`; the server does not call a separate model. For multiple choice it saves a pool of five or six concise options (maximum 100 characters each) including exactly one correct answer. Both Quiz and the lesson study screen sample three distractors and the correct answer and shuffle the four displayed choices once per question/session. Existing cards without saved questions keep their prior fallback. Local tests cover six-option persistence, four-choice sampling, validation, atomic writes, and cross-account isolation; they do not establish model output quality or hosted client compatibility.

Lesson creation and card addition now return the created card IDs and terms so the client can associate generated questions with the correct cards without a separate listing step. Supplying language details to a knowledge lesson is rejected instead of silently discarding the details. These changes and the updated lesson-creation SQL are local only.

Saved practice questions can also be replaced or deleted through the MCP; updates are scoped to an owned lesson and card, and deletions require explicit confirmation. The local broker flow verifies owner updates, deletion, invalid confirmation, and cross-account denial.

For new content, clients can use `create_lesson_with_practice` or `add_cards_with_practice`: the user’s LLM supplies at least one multiple-choice and one recall question for each card, and the database commits or rolls back the whole batch. The older individual tools remain available for empty lessons and incremental editing. Local database tests verify rollback; the local broker flow verifies tool discovery and both atomic creation paths. This relies on the MCP client choosing and calling the tools; model quality and hosted-client behavior remain to be verified.

When a creation or question-save response is lost, the tool now reports the outcome as unknown and asks the client to inspect existing content before retrying. A local MCP transport test covers this response for all five creation paths. This reduces misleading retries but does not provide idempotency: identifying matching content can be ambiguous, and safe automatic retries still require a persistent, user-scoped idempotency design and concurrent/failure testing before release.

The broker derives OAuth protected-resource metadata from its validated configured origin. The default-disabled runtime returned 503 in local Wrangler, and the full local OAuth flow passed after explicit test-only enablement. Non-local operation now additionally requires `BROKER_TEST_ONLY_ALLOW_EVENTUAL_CONSISTENCY=true`; this deliberately named override is only for isolated testing with disposable accounts and does not make KV-backed revocation or refresh safe for real users. A staging environment needs its own HTTPS origin, Supabase client and callback, KV namespace, and independent security review; enabling either flag is not itself deployment approval.

The isolated Workerd broker test checks authorization-server discovery (issuer, S256 and private-key JWT), resource metadata and the unauthenticated challenge. It rejects an unrelated resource at authorization, authorization-code exchange and refresh, and verifies the rejected refresh does not reach the upstream provider; the correct resource succeeds. The full local broker test uses synthetic RS256 signatures, a `jwks_uri`, and metadata with both `none` and `private_key_jwt`, resembling the [published ChatGPT client metadata](https://chatgpt.com/oauth/client.json); another test covers ES256 with embedded keys. Both metadata and upstream endpoints are mocked, so this is not a real ChatGPT connection, a public-network fetch test, or proof of hosted configuration.

Question input objects now use a flat schema with a `question_type` enum and a described options field; server-side validation still enforces each question type’s rules. The MCP tool catalogue and local end-to-end flow pass with this schema. No claim of compatibility with hosted ChatGPT, Claude, or Gemini clients is made until each is tested.

MCP question writes require the card revision last read by the model; creation and replacement reject it if the card changed. Atomic card-and-practice creation assigns the revision within its transaction. The database trigger locks the source card and rejects a mismatched supplied revision. The native question generators now read card text and revisions from the database before generating and pass the snapshot revision on insert. For backward compatibility, direct legacy inserts that omit a source revision are stamped at insertion time and do not get the same stale-input guarantee. The full MCP flow and database rejection cases passed in a newly isolated local test project. The two native question generators now pass Deno type checking with the pinned OpenAI SDK 6.49.0, and a mocked request verifies the existing parameters. Validate actual model calls in staging before deploying those functions.
