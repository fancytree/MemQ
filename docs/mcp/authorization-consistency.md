# Authorization consistency design (local experiment only)

The broker is disabled by default. `COORDINATED_LOCAL_TEST=true` is restricted to local HTTP broker and Supabase URLs and is an integration experiment, not a production release path. Never connect it to real accounts.

The local path uses a per-grant Durable Object for state, encrypted upstream sessions and a registry of provider-issued token hashes. It registers token hashes before returning successful issuance responses and uses the registry for standard revocation after the provider authenticates the client. Access and refresh entries have lower and upper expiry bounds; requests in the uncertainty interval fail closed. Refresh bounds are fixed on the initial token issuance and preserved across later rotations, matching the configured fixed-lifetime provider behavior. Local tests cover this invariant and a full OAuth flow, but long-duration and provider-version compatibility still need verification. Personal-center disconnect, public clients and client-secret POST/Basic have local OAuth integration coverage. Unknown tokens return the provider's 200 response without revoking a grant; a different client cannot revoke it. Private-key assertion routing has mock-provider coverage and a guarded local broker authentication test; full broker lifecycle and cross-region verification remain outstanding.

The local-only callback now initializes a pending coordinator before returning an authorization code. The user can disconnect that pending grant, after which its code cannot be exchanged. A local OAuth test covers cancellation before exchange, and a Durable Object test confirms that only one concurrent claim succeeds. There remains a small pre-initialization window after the provider creates a grant; disconnect in that interval returns 503 rather than falsely reporting success. The local experiment relies on the installed provider's authorization-code format and must not be treated as a stable production integration.

Pending authorizations schedule an alarm to clear the encrypted session after ten minutes, and code exchange independently checks the deadline. Workers runtime tests force an expired alarm after object eviction, verify early alarms reschedule without clearing active sessions, and inject a scheduling failure to confirm the session is cleared. The normal local OAuth flow also passes. Real-time delivery, deployed restart and multi-location behavior still need verification before release.

In the local experiment, token issuance schedules cleanup of the encrypted session after the last relevant token's upper expiry bound. Explicit revocation atomically clears the encrypted session and token hash records while retaining a revoked tombstone, so retry cannot revive the grant. If an authorization code was claimed but token registration never completes, its original pending deadline still clears the session. Local Workers tests cover active-session expiry after eviction, explicit cleanup and alarm scheduling failure; the isolated OAuth and failure-retry flow also passes. Deployed alarm delivery, migration of prior local records, retention costs and all production failure boundaries remain unverified.

`AssertionReplay` is a per-assertion Durable Object prototype. Local Workers tests allowed only one of 20 simultaneous adapter claims, confirmed a marker survives eviction, and exercised expiry cleanup, early-alarm rescheduling and alarm failure. An opt-in localhost-only adapter intercepts the installed provider's replay-marker read after its signature verification; the provider is pinned to 1.2.4 because this adapter depends on its internal get-then-put sequence. The adapter fails closed if its coordinator is unavailable. Local Workers tests use synthetic ES256-signed assertions and mocked client metadata: an invalid signature cannot consume the marker, and only one of 20 concurrent valid assertions gets past client authentication. An isolated provider handler exercises PKCE authorization, token issuance, resource access, refresh, replay rejection and provider-level revocation. Another test uses the actual broker consent and callback, coordinated token exchange, refresh and disconnect paths with mocked upstream authentication and metadata. Broker CIMD is available only in the explicitly enabled local experiment with replay protection and a local upstream; missing safeguards fail closed. Real metadata retrieval, real upstream authentication, real clients, operational cost and multi-location behavior still require validation; this is not evidence of production readiness. Never claim a replay marker from unverified assertions.

A local fault-injection test makes coordinator revocation fail after the real provider handles a revoke; a retry then succeeds without relying on provider KV records. Separate tests cover coordinator restart, concurrent refresh, owner isolation and revocation while a refresh is in flight. The signed-client broker test also verifies that another signed client cannot revoke the grant, that a repeated refresh assertion is rejected, and that neither access nor refresh succeeds after revocation. These tests do not establish multi-location behavior or all failure boundaries. The previous pending-revocation table is no longer on the active local revocation path and needs a cleanup/migration decision before any deployment. Token expiry, lifecycle, key provisioning and rotation, user-facing reconnect, provider-internal revocations, reauthorization behavior and real-client compatibility still require review and verification. The local fixture exposes unauthenticated RPC and must never be deployed.

## Provider integration findings

The provider's exchange callback supplies verified user, client and grant IDs. The local experiment places bound grant identity in authenticated props for the resource handler and intercepts standard revocation using the coordinator's issued-token registry. Provider-internal revocations and administrative client deletion remain separate paths that must be handled before release. Unverified token components are used only for routing and must never be treated as authorization evidence.

The provider's `completeAuthorization` also revokes prior grants for the same user and client by default, without coordinating those objects. Reauthorization must account for this path as well; merely handling explicit disconnects is insufficient. `verifiedGrant.ts` supplies a tested subject/props binding check used by the local-only request path.

A deterministic test now simulates a lost response after a successful coordinator commit: the new encrypted upstream credential remains stored, not the old one. This does not establish whether the OAuth provider can safely complete or retry downstream token issuance after that ambiguity.

The current provider stores grants and access-token records in eventually consistent KV. Do not enable it for real users until the behavior below is implemented and independently tested. Local single-runtime tests do not establish these guarantees.

## Required behavior

- Once a disconnect operation succeeds, new requests and refreshes for that grant must fail from every location. An already-running operation may finish; the UI and documentation must not imply otherwise.
- Concurrent refreshes for one grant must not submit the same upstream refresh credential twice, lose the new credential, or revive a revoked grant. Distinct grants must be independent.
- Never return upstream Supabase credentials to a client or write them to logs. An unavailable consistency service fails closed.

## Candidate architecture

Use a strongly consistent, per-grant coordinator keyed by an opaque grant identifier. Route **every** protected request and refresh through it, and route all disconnect paths through the same coordinator. Its persisted state includes the owning user, status, and the minimum encrypted upstream session material required to refresh. Do not trust unverified bearer-token components to select an owner or authorize an operation: first validate the token and compare the authenticated subject and grant identity against the coordinator's state.

Refresh is a state machine, not just a storage write: accept one in-flight upstream exchange for a grant; re-check status before committing rotated credentials; if a revoke wins during the exchange, discard its result and do not issue a usable new token. A network failure after the upstream has rotated a credential but before the new credential is persisted is an ambiguous outcome: recover only if the upstream protocol supports it, otherwise require the user to reconnect. Never silently restore the old credential as if rotation had not happened.

Revocation first records a durable revoked state in the coordinator and only then reports success. KV token cleanup and upstream revocation are subsequent cleanup; neither can be treated as the source of truth for the immediately enforced state. Define handling for coordinator creation, grant expiry, orphaned state, reconnects, and failures before implementation. Existing grants cannot be migrated implicitly without a secure mapping and a deliberate rollout.

The installed Cloudflare provider validates tokens from KV before invoking the application and has separate authorization, token, and connection-management paths. A per-grant coordinator cannot be bolted onto only the resource handler: refresh, token issuance, callback completion, and **all** revocation paths must participate. Evaluate whether the provider's supported extension points can enforce these invariants; if not, replace the affected authorization implementation rather than assuming a KV-shaped adapter makes a multi-step refresh atomic.

## Verification before release

Use local deterministic tests with controllable delays and failures, then staging tests from different network locations:

1. Request accepted before revocation may finish; one started after successful revocation is denied, including with a previously cached access token.
2. Two simultaneous refreshes result in at most one upstream rotation; the other receives a valid coordinated result or a recoverable error.
3. Revoke at each refresh boundary, including after upstream success but before local persistence. No later request or refresh revives the grant.
4. Restart the coordinator between each state transition and inject storage and upstream failures. Fail closed and do not log credentials.
5. Two grants for one account remain independent, and a different user cannot inspect or revoke either grant.
6. Check real provider callback, hosted client, and multi-location behavior. Confirm operational cost, latency, retention, cleanup, and deployment migration before enabling.

Cloudflare documents [strongly consistent per-object state](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/) and [eventual KV visibility](https://developers.cloudflare.com/kv/concepts/how-kv-works/). These primitives do not by themselves prove the end-to-end authorization guarantees above.
